# Qalam Studio: notes for coding agents

- **UI:** a React single-page app built with Vite. `index.html` loads `src/main.tsx`, and `src/ui/App.tsx` picks the page from the address (`src/ui/routes.ts`). Moving between pages is a full page load, so there is no client router.
  - Every page outside the canvas sits in `PageFrame` (`src/ui/frame/`). It provides the top bar, a sidebar (the organization's places and products; ⌘\ folds it to a rail), toasts, dialogs, and a page ⌘K (`PagePalette`, keys in `src/commands/pages.ts`).
  - Each place has its own address, `/o/<org>/goals|problems|evidence|decisions|connections` (`src/ui/frame/places.ts`). Build it with `placeHref`. The old `/boards`, `/topics` and `/sources` redirect (`MOVED_PLACES`), and so does the home's old `?tab=`.
    - Goals is the tree with each board under its goal, then the boards with no goal. Problems is every need page, filtered by goal (`ProblemsList`). Evidence is the sources and the segment and product pages.
    - The home leads with your goals and their top problems (`YourGoals`), then Needs a look grouped by goal, then problems no goal covers.
  - People see one word per thing: Goal (an outcome; Sub-goal), Problem (an opportunity, or a topic page about a need), Solution, Test, Board (a Discovery project). Type names in code stay as they were (`KIND_LABEL` in `src/discovery/kinds.ts`, `TOPIC_KIND_LABEL`). A board's chrome drops the design tool's menus, Keys list and status line.
  - A board's rail shows Home, Goals, Problems and Connections above its own panels (`RailPlaces`). They save the board before leaving (`leaveTo`).
- **Server:** `server/` is a small Hono app (`server/app.ts`). Each route in `server/routes/*.ts` takes a standard `Request` and returns a `Response`; AI routes stream NDJSON. Model calls happen only there.
  - `pnpm dev` runs Vite on 127.0.0.1:3101 with the server mounted at `/api/*` (`server/vite.ts`). An edit to a route or to `src/ai` takes effect on the next request.
  - `pnpm build && pnpm start` serves `dist/` and the server from one Node process (`server/serve.ts`).
  - Requests are checked by `server/guard.ts` (Host must be this machine; writes must come from this origin; optional launch token).
- **Desktop app:** `electron/main.ts` serves the built UI at `qalam://app` and forwards `/api/*` to the core, a background utility process (`server/core.ts`), over a message port (`server/rpc.ts`). No network port is opened, except the one-time sign-in listener on 127.0.0.1 (see Connectors). `vite.desktop.config.ts` bundles both into `out/`, so the installed app needs only Electron.
  - `pnpm desktop` builds and opens it; `pnpm desktop:dev` opens the window on the Vite dev server.
  - `bin/qalam-studio.mjs` is the `npx qalam-studio` launcher.
  - **The menu bar (`electron/tray.ts`):** Qalam stays there when its window closes (`desktop.json`'s `keepInMenuBar`), so the inbox and connectors keep working.
    - Its menu (`trayMenuTemplate`, pure) shows whether Qalam AI is ready, from `/api/health` through `coreFetch`, plus opening at login.
    - ⌃⌥Space opens quick capture: a small window on `/capture` that posts a note, quote or link to `POST /api/org/:org/quick` (`server/quick.ts`). That writes a file into the inbox, which takes it from there.
  - The page's security policy is in `electron/assets.ts`. It allows `unsafe-eval` only because the prototype runner evaluates compiled code (`src/ui/prototype/runtime.ts`).
  - `pnpm dist:mac` packages the Mac app (Apple silicon): `scripts/stage-app.mjs` puts what the installed app loads in `release/app` (out/, dist/, and node-llama-cpp installed by npm, since this package's own `package.json` lists Electron for npx), then electron-builder runs with that folder as its project (`electron-builder.yml`, paths relative to it). The models process and Ask's bridge run the app's binary as Node (`ELECTRON_RUN_AS_NODE`), so never turn that fuse off. The installed app takes the login shell's PATH (`loginShellPath`, `server/claude.ts`) and updates itself from GitHub Releases (`electron/updates.ts`). `.github/workflows/release.yml` builds a tag into a signed, notarized draft release; `homebrew.yml` writes the cask into the tap when a release is published (`docs/releasing.md`).
- **Organizations and products:** pages live under their organization: `/o/<org>` is its home (`src/ui/home/Home.tsx` with `src/ui/org/`), `/o/<org>/d/<id>` a board; `/` and addresses from before (`/d/<id>`) find the organization and move there (`src/ui/App.tsx`). Build links with `projectHref`/`orgHref` (`src/projects/model.ts`), never by hand. A board (`Project.product`) and a source (`SourceRecord.product`) are for one product or the whole organization; products are `products/<slug>.md` and the organization's own context `about.md` (`src/org/context-md.ts`), and Qalam AI reads the board's with `contextFor` (`src/org/context.ts`). Sources belong to the organization and list the boards that use them (`boards`); taking one off a board keeps it. A card's quote names its piece (`OstEvidence.piece`, `hub:quote:<id>`).
- **Storage:** an organization is a folder in `~/Qalam` (`QALAM_HOME` moves it; tests and browser checks must point it at a scratch folder). `server/org/` owns it: `codecs.ts` turns projects and sources into readable files, `store.ts` keeps the index, versions (409 on a stale document save) and the folder watcher, `routes.ts` serves `/api/orgs` and `/api/org/:org/*`. The browser side is `src/org/` (client, startup gate, live changes, conflict choice, import from browser storage); the repos in `src/projects/db.ts`, `src/discovery/db.ts`, `src/knowledge/db.ts` and `src/ui/ai/chatDb.ts` go through it.
- **Goals:** one tree per organization in `goals.md` (`src/goals/`, codec `goals-md.ts`): the North Star under its heading with each goal nested under the goal it feeds, then "Not under a goal yet". It's the only place a goal lives; the About and product files no longer hold goals (`legacyGoals` moves an old "## Goals" section in once, `migrateGoals` at store open, ids fixed so two computers write the same file).
  - A board's outcome card is its goal on the canvas: the goal says which card (`on: {board, card}`), and the card keeps a copy of its words, number and stage to paint. While the board is open, `src/ui/discovery/goals.ts` brings the two together (`reconcile` in `src/goals/mirror.ts`): a goal's change elsewhere reaches the card outside undo (and the undo history keeps it), an edit on the board goes to the goal. A new outcome card gets its goal (one already named in its words first). The server never writes a board for a goal.
  - Goal decisions (target, a number moved by hand, status, the goal it feeds, the North Star) are found by comparing the tree before and after an API write (`goalDecisions`, `src/goals/decisions.ts`), recorded under the board "goals", undone when taken back within 10 minutes; a hand edit of the file records none. The board's recorder skips a linked card's number and stage (`DiffContext.linked`).
  - Qalam AI hears the goals through `goalsText` (`src/goals/text.ts`) wherever it hears the About; goals are `context` pieces with sub `goal` (`hub:goal:<id>`), under their parent and linked to their card (`for`). Which goals are this computer's person's: `mine` in `.qalam/local`.
  - **A goal's page** (`/o/<org>/g/<id>`, `src/ui/goals/GoalPage.tsx`, data from `goalPage` in `server/org/goals.ts`): its number, the goal it feeds and the goals under it, the board working on it, the problems behind it and its decisions. "Work on it" opens the goal's board with `?problem=<topic>&under=<card>`, which puts the problem under the outcome once (`addProblemFromUrl`); no board yet starts one whose outcome is the goal (`startBoardForGoal`).
  - **Which problems bear on which goals** (`hub/bearings.jsonl`, folded by `foldBearings`): one call (`bearingsCall`, `src/ai/goals.ts`) reads need pages against goals; `sanitizeBearings` keeps a link only when its ids were sent, it cites its problem's own lines and its words and numbers are in them (or the goal's number). A long page sends the lines search ranks nearest the goal (`nearGoals`). "Find problems" runs it for a goal and the goals under it (replacing Qalam AI's earlier links there); `startBearings` runs it after Qalam AI files material into need pages (topic events with `filed`), for those pages against every active goal. A person's link or unlink stands: Qalam AI never makes a link they took off. Each call's trace goes in `chats/goals/traces`. `rankForGoal` (`src/goals/problems.ts`) orders the problems behind a goal: direct ones first, then by sources, quotes and newest; a sub-goal's show through it.
  - Needs a look: a goal's number not updated in weeks is checked on the goal (`runChecks` with `goals`), and each notice carries the goals it bears on (`withGoals` in `server/org/notices.ts`).
  - **What we don't know yet:** `gapsOf` (`src/goals/gaps.ts`, pure, no tokens) finds a goal's gaps: no number, where it stands, no target, no problems, a problem only the team raises, a problem no segment page cites, its pages' open questions. Each gap's key stays the same while it's open.
    - **Jobs** close them (`src/goals/jobs.ts`, `hub/jobs.jsonl`: a job's line, then a line per change, folded by `foldJobs`). One call (`jobsCall`, `src/ai/jobs.ts`) plans them from the goal, its gaps and problems, the tools here and whether each is connected (`jobTools`), and the segment pages and people the sources name. `sanitizeJobs` keeps a job only when its gap, tool and people were sent, its words and numbers are in what was sent, and its gap has no open job.
    - A search job runs in its tool (`searchForJob`); the items picked go through `importItems` like any material, then `flushBearings` links what was filed to the goals at once, and the job is done with what came of it (`takeInForJob`, `server/org/jobs.ts`). A numbers job reads the goal's number from PostHog (`MetricSource`, `src/ui/numbers/`). A talk job is handed over: its questions and who to ask; notes posted to `/capture` with the job's id are kept on it and linked at once (`noteForJob`). A read-code job is answered from the product's code once it's connected (see Product code).
    - The goal page lists each gap with its job (`src/ui/goals/Unknowns.tsx`); the home's goal cards show each goal's next job (`useJobs`).
  - **What others aim for and Break it down** (`server/org/outside.ts`, kept per goal in `hub/goals/<goal>.json`, `changeGoalWork` in the store):
    - What others aim for: the research step looks it up on the web (purpose `goals`, `research()` in `src/ai/server.ts`), the core reads the pages it links itself (`fetchGuarded`, `htmlText`), and one call (`claimsCall`, `src/ai/outside.ts`) picks out the numbers others report from excerpts around the numbers the notes name (`pageExcerpt`). `sanitizeClaims` (`src/goals/outside.ts`) keeps a claim only when its quote is on its page word for word and its number is in the quote. They're never sources, never customer evidence, never a goal's number.
    - Break it down: one call (`breakdownCall`, `src/ai/breakdown.ts`) reads the goal and the goals above, the levers the person picked (their answer), a pack of their material anchored on the goal and what others report, and proposes the goals under it, each on a lever. `sanitizeBreakdown` keeps a part only when its words and numbers are in what it cites or in the goals above (what others report shows beside a part, never in it), and a number only from their words. Whether the parts make the goal's number is code's arithmetic (`checkParts`, `src/goals/math.ts`: a product or a sum, a rate in % multiplying as a fraction, within 5%). Accepting puts a part in `goals.md` under the goal (`decidePart`).
- **Decisions:** a board's decisions are found by comparing it before and after a change (`decisionsFromDiff` in `src/decisions/diff.ts`), never by instrumenting commands, so every way of changing the board is covered. `src/ui/decisions/recorder.ts` runs that 1.5 s after changes settle, sends what it found to `decisions/<YYYY-MM>.md` (`server/org/store.ts`, Markdown in `src/decisions/format.ts`), asks why on big ones (`WhyPrompt.tsx`) and marks a decision undone when it's taken back. Accepting or discarding Qalam AI's proposals goes through `recordAccepted`/`recordDiscarded`. Adding or rewording a card is not a decision.
- **Search:** the organization's knowledge is indexed as pieces (one fact each: a quote, need, card, assumption, decision, line about a product) with links between them (`src/hub/pieces.ts`). `server/index/` keeps `.qalam/index.sqlite` current from the store's change events (only what changed is written; it can always be deleted and rebuilt) and searches by words (FTS5), meaning (vectors) and links, fused by rank (`server/index/search.ts`); `packFor` fits the result into a token budget with `[k1]` ids (`src/hub/pack.ts`). The embedding model runs in its own process (`server/models/`, node-llama-cpp, downloaded on first use). Change a step only with `pnpm eval:retrieval` before and after: it scores search on a labelled sample organization (`eval/retrieval/`), and its numbers chose today's setup.
- **Calls with the organization's knowledge:** a board's AI calls (draft, extract, synthesize, dump-place) pack what bears on them on the client (`src/org/pack.ts` → `POST /api/org/:org/pack`), leaving out what the call already sends, and pass it as `context` (block, `k` ids, which ids are quotes); routes stay stateless (`withKnowledge`, `knowledgeBlock`, `withPieceReliance` in `src/ai/discovery.ts`). Quotes from other sources load as "visiting" sources (`src/ui/discovery/sources.ts`) so proposals can attach them; accepting puts the source on the board. `recordCall` (`src/ui/discovery/knowledge.ts`) keeps each call's trace: what it was given, and only the cited ids it was sent. No index (Node 22) means no context, and the calls work as before.
- **Topic pages:** one Markdown page per customer need, segment and product (`hub/topics/<slug>.md`, codec `src/hub/topic-md.ts`): We know · We believe · Against · Open questions, and History. Qalam AI files new material into them (`src/org/filing.ts` → `POST /api/topics`, prompt and schema in `src/ai/topics.ts`) after a board reads sources or places a brain dump (`src/ui/topics/filing.ts`), and from the home's Topics tab; each quote sent is marked in its source's `filed`, so it isn't sent again. `sanitizeFiling` (`src/hub/topics.ts`) keeps a line only when every piece it cites was sent and its quoted words and numbers are in them, moves a "We know"/"Against" line resting only on the team's words to "We believe", and never lets Qalam AI rewrite a person's line (it can dispute it). The store applies a filing to the pages as they are (`fileTopics`, one lock with people's edits). Each line is indexed as a `page` piece linked to what it cites (`topicPieces`); packs put page lines found near the top first.
- **Needs a look:** `runChecks` (`src/hub/checks.ts`, pure, no tokens) finds what a team should hear about: Qalam AI's disputes on topic pages, a need customers keep raising that no board has, the same need on two boards, a parked or dropped card new evidence backs, a test running too long, a build on an untested risky assumption, an outcome nobody updates, a page whose pieces are gone. Each notice's key says what it's about and how strong it is, so a dismissed one stays dismissed until it grows. `server/org/notices.ts` runs the checks on request (after the index catches up) and leaves out what's dismissed; dismissals and Review now's findings go in `hub/notices.jsonl`, cards linked as the same need in `hub/relations.jsonl` (append-only, union-merged in Git; links become `same` edges in the index). The last visit is per computer (`.qalam/local`). Review now runs in the core (`server/org/review.ts`, `structured()` in `src/ai/server.ts`): `reviewMaterial`/`sanitizeReview` (`src/hub/review.ts`) keep a finding only when it rests on ids it was sent, its quotes and numbers found in them; a review replaces the last one's findings. The home shows them (`src/ui/org/NeedsALook.tsx`); a board marks its cards (`noticed` in the painter's input) and the card panel says why.
- **What to work on next:** the home ranks the need pages by the customer evidence their "We know" lines cite: sources first, then quotes, then the newest (`rankNeeds` in `src/hub/needs.ts`, pure).
  - The `pattern` check shares its count (`needEvidence`).
  - Each need also carries what speaks against it, the segment pages citing the same words, quotes added per week, and the boards that have it.
  - `GET /api/org/:org/needs` serves the ranking (`server/org/needs.ts`). `knowledgeInputs` there is what the notices read too.
  - A need's topic page opens on the same summary (`summary` in the topic view, `NeedStrip`), and "Start a board" makes it a board's first card (`startBoardForNeed`).
  - A card's Evidence in the card panel opens on a strip in the same words (`evidenceSummary` in `src/discovery/evidence.ts`): strength by its customers' quotes' sources, quotes and sources, against, who. Then one line per piece of evidence (`evidenceRows`), whole on a click.
  - Small marks for amounts and states are in `src/ui/viz.tsx`.
- **Capture:** material added to the organization rather than a board goes through `captureSource` (`server/capture.ts`) in the core: kept as a source with no board, read (the extract call), filed into the topic pages (`fileMaterial`, `src/hub/filing.ts`, which the window's `src/org/filing.ts` also runs with its own dependencies), then placed: one synthesize call over the boards' trees, its answer split by board before `sanitizeSynthesis`, each board's proposals kept in its own file (`hub/placements/<board>.json`, `setPlacements` in `server/org/store.ts`, so accepting on a board never races a capture writing the source). A board finds them through `GET /api/org/:org/placements` and reviews them as its own (`{ kind: "placed" }` in `src/ui/discovery/review.ts`); "Needs a look" says they wait. The calls are described once (`extractCall`, `synthesizeCall`, `topicsCall`) for the routes and the core's `structured()`. Reading files is shared (`src/discovery/ingest/core.ts`, readers passed in): the window reads with pdf.js in a worker and DOMParser, the core with pdf.js's legacy build in-process and mammoth (`server/ingest.ts`). The home's Add reads in the window and posts to `/capture`; the inbox folder (`server/inbox.ts`, started for each store as it opens; the organization opened last opens when the core starts, `openLastOrg`) reads in the core, claims each file by moving it into `inbox/.taking/` (two Qalams on one folder never take a file twice), then moves it to `inbox/added` or `inbox/not-read`. One store per organization per process (`storeFor`), however many requests ask at once.
- **Connectors:** the catalog's four groups are in `src/connectors/catalog.ts`. Material comes in through three paths:
  - **Claude Code's own connectors** (claude.ai's included), used through it. `claude mcp list` (`parseMcpList`) is run only on demand and kept 5 min.
    - The tool-runner (`runTools` in `server/connectors/claude-code.ts`) makes the calls code planned in a short `claude -p` whose only allowed tools are those, and keeps each answer as the server gave it.
    - It loads the user's settings, so it starts their MCP servers first and is slow (about a minute).
  - **Qalam's own sign-in** to the service's MCP server (`ConnectorDef.mcp`: Notion's `https://mcp.notion.com/mcp`, Intercom's US and EU servers, Slack's, Linear's, Atlassian's), in `server/connectors/oauth.ts`:
    - Notion, Intercom, Linear and Atlassian let Qalam register itself. Slack lets no app do that and takes only apps made for a workspace (`mcp.ownApp`, `src/connectors/slack.ts`):
      - The card's "Set up…" opens Slack's "Create an app" with Qalam's manifest filled in (`slackAppLink`: read-only user scopes, a bot user that `v2_user` sign-in wants, `is_mcp_enabled`, and `http://localhost:38712/callback`).
      - The app's client ID and secret go in the Keychain (`keepApp`, `PUT /api/connectors/:id/app`); an app with PKCE needs no secret. Its sign-in comes back only to that fixed address, listening on 127.0.0.1 and ::1.
      - The app is never dropped behind the person's back (`ownClient`), even when Slack refuses a refresh.
      - Slack's token endpoint says no with a 200 and `{ok: false, error}`, which `sayNo` turns into the OAuth error it is, in words. "Not enabled" on the first call means the app's MCP switch is off.
    - `mcp.scope` narrows what Qalam asks for (Intercom: `mcp`, not Fin Operator's `operator`; Linear: `read`, so the token can't reach its write tools). `mcp.regions` lists a service's servers by region; the card picks one, and the route takes only a catalog URL.
    - Connectors that share an account (`mcp.account`: Atlassian's, for Jira and Confluence) keep one pair of Keychain items under its id, and their cards say "Sign in with Atlassian". One sign-in connects each of them whose tools the server offers (a site may have Jira and no Confluence). Disconnecting either disconnects both.
    - Atlassian is reached at `https://mcp.atlassian.com/v1/mcp`, where its page asks which apps to allow. v2 (`/v2/mcp`) would take read-only scopes, but its sign-in turns apps that come back to this Mac away after consent ("Incorrect request parameters", October 2026; adding `read:account` didn't help here). Codex and the Python MCP SDK report the same.
    - OAuth 2.1 with PKCE, Qalam registering itself, through the MCP SDK's `auth()`. The page opens in the system's browser (`/usr/bin/open`, web addresses only), and `POST /api/connectors/:id/signin` streams its address for a link.
    - The page comes back to a listener on 127.0.0.1, the one network port Qalam opens. It is open only for that sign-in: it takes one answer with the sign-in's state on this Host, or closes after 5 minutes or on Stop (`DELETE …/signin`).
    - The answer's `iss` must be the issuer. The code is exchanged, and one call (`listTools`, the recipe's tools present: a material recipe's search and fetch, a work recipe's status call) is made before anything is kept.
    - The registration goes in the Keychain as `connector:<id>:client`, the tokens as `connector:<id>:oauth`, and the settings say `{ via: "oauth", url }`.
    - Calls go straight to the server (`withSignedIn`, `server/connectors/mcp.ts`), one session per connector at a time. A token is refreshed when the server asks.
    - A refused refresh drops the tokens, and the card says "Sign in again". A service that's down keeps them. Disconnect revokes them at the service (RFC 7009) before forgetting them.
    - Both servers keep the platform's `Response` global (`overrideGlobalObjects: false`): the SDK checks `instanceof Response`, and Hono's own class broke that.
  - **A token Qalam keeps in the Keychain:** for Notion, its own API (`server/connectors/notion-api.ts`).
  - Recipes say what to call and how to read the answer (`src/connectors/recipes.ts`). Picked items go to `captureSource` as `kind: "connector"` with their URL as `origin`; the same origin with the same words is skipped (`importItems`).
    - Slack's: `slack_search_public_and_private` with the person's own query (Slack's modifiers work), whose Markdown answer is read by its message links (`slackHits`: `/archives/<channel>/p<ts>`, a reply's `thread_ts` names its thread), then `slack_read_thread`.
    - Confluence's (`src/connectors/confluence.ts`): every Atlassian call names its site (`cloudId`). A recipe can name a first call for it (`Recipe.site`): `getAccessibleAtlassianResources`, the first site with Confluence. Then `searchConfluenceUsingCql` (CQL `text ~ "…"`, the words inside the quotes) and `getConfluencePage` as Markdown, each hit carrying its site (`Hit.site`). Written from Atlassian's docs, not yet checked against a real site.
    - Intercom's: `search` with `object_type:conversations q:"…"` (the words stay inside the quotes), `fetch` by `conversation_…` id. `intercomText` turns a conversation into who said what ("Customer (name): …", "Team", "Note"), HTML taken off with `htmlText` (`src/discovery/ingest/text.ts`); a shape it doesn't know reads as its fields (`captureText`).
  - How each is reached is in the settings' `connectors`.
  - Importing works for Notion, Intercom, Slack and Confluence today. Drive and the rest show where they stand ("In Claude Code", "Coming next").
  - **Work:** a solution card links issues, PRs and designs by address (`OstCard.work`, `parseWorkUrl` in `src/connectors/work.ts`).
    - Linear and public GitHub say where each stands. Answers are kept per computer in `<org>/.qalam/local/work.json` (`workStatuses`, `POST /api/org/:org/work/status`).
    - Linear signed in: its MCP server's `get_issue` by identifier, asking only for `title`, `status` and `statusType` (never the description), all of a request's issues in one session (`WORK_RECIPES` in `src/connectors/work.ts`). The answer's `id` is the identifier; `linearIssueStatus` drops an answer about another issue. A missing issue is an error answer, shown as "Can't see it". Checked against a real workspace.
    - Linear with a pasted key: its GraphQL API.
    - Jira signed in (Atlassian): `getJiraIssue` on the link's site (`cloudId` takes the site's address), asking only for the summary and status. `jiraIssueStatus` reads Jira's status category (a done one named "Won't Do" reads as canceled) and drops an answer about another issue. Written from Atlassian's docs, not yet checked against a real site.
    - The card shows the furthest one along after its kind (`work` in the painter's input).
    - The stage stays the team's. The `work-drift` check says when the tool and the stage disagree.
  - **Numbers:** an outcome's metric can read `current` from a saved PostHog insight through Claude Code's PostHog server (`src/connectors/numbers.ts`, `server/connectors/numbers.ts`).
    - Code reads the number from PostHog's own answer (`insightNumbers`) and asks which series when there are several.
    - The metric keeps `source` and `readAt`. A read is not a decision (`decisionsFromDiff` skips it), and it quiets the "nobody updates it" check.
    - A saved funnel gives each step's count too (`steps` in `insightNumbers`); a goal's funnel counts are kept in its work file and its biggest drop is code's arithmetic (`funnelDrops`, `src/goals/math.ts`).
  - **Product code, read-only** (`server/code/`, Connections' "Product code"):
    - A repository is copied into `<org>/.qalam/code/<owner>__<repo>` (out of Git) through this Mac's GitHub CLI (`gh api …/tarball`: gh's own sign-in, Qalam never sees the token), or with Qalam's own GitHub sign-in (`server/code/github.ts`: the Qalam GitHub App's device flow, Contents and Metadata read-only, the token in the Keychain and only ever in a request's header; on only when `QALAM_GITHUB_CLIENT_ID` is set). A folder on this Mac is read where it is, never written. Which repositories this Mac reads, for which product: `code` in `.qalam/local`.
    - The tarball is someone else's: `untarInto` (`server/code/tar.ts`) keeps only regular files under its top folder, nothing absolute or climbing out, no links, only code and text (`keepPath`: nothing vendored, built, generated or binary), each file and the copy under a size.
    - The scanner (`scanCode`, `src/code/scan.ts`, pure) lists the analytics events the code sends (PostHog, Segment, Amplitude, Mixpanel, Firebase, gtag) and its screens and routes, each with its file and line.
    - The reader writes the main flows as steps (`src/ai/code.ts`): Claude Code with Read, Grep and Glob only, run from an empty folder with the copy added beside it, so nothing in the repository (its CLAUDE.md) is taken as instructions; with a key, one call over excerpts. `verifyFlows` (`src/code/map.ts`) keeps a step only when its file is in the copy, its snippet is in that file and its events are on the scanner's list; a flow can name the goal its events measure (that goal's funnel, `funnelOf`).
    - What each product does today goes in `hub/maps/<key>.md` (`mapToMarkdown`, each step's record in a comment), shown on Evidence and indexed (`mapPieces`, sub `map`). A read-code job's question is answered the same way (`answerFromCode`), kept only where `verifyAnswer` finds what it cites in the files.
